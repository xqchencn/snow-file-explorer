# Snow App 文件浏览器

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)
[![Latest Release](https://img.shields.io/github/v/release/xqchencn/snow-file-explorer?display_name=tag)](https://github.com/xqchencn/snow-file-explorer/releases)

Snow App 的本地项目文件浏览器插件。它跟随 Snow App 当前打开的项目，提供文件树、代码与图片预览、Markdown 预览、Git 变更管理、交互式终端和项目命令运行。

## 适用版本

- 需要已安装并支持插件的 [Snow App](https://github.com/MayDay-wpf/snow-app)。
- 插件操作的是 Snow App 当前激活项目目录，不在插件内单独选择项目。
- Git 功能需要当前项目是 Git 仓库，并且本机已正确配置 Git；提交和推送仍遵循仓库自身的权限与远端配置。

## 安装

### 推荐：安装 GitHub Release

1. 打开本项目的 [Releases](https://github.com/xqchencn/snow-file-explorer/releases) 页面，下载最新版本的 `snow-file-explorer-vX.Y.Z.zip`。
2. 将压缩包内容解压到下面的插件目录，并确保 `plugin.json` 直接位于插件目录根部：

   **Windows**

   ```text
   %USERPROFILE%\\.snowapp\\plugins\\com.github.xqchencn.snow-file-explorer
   ```

   **macOS / Linux**

   ```text
   ~/.snowapp/plugins/com.github.xqchencn.snow-file-explorer
   ```

3. 完全重启 Snow App，或在宿主的插件管理界面重新加载插件。
4. 在 Snow App 侧边栏打开“文件浏览器”。

解压完成后的目录结构应类似下面这样：

```text
com.github.xqchencn.snow-file-explorer/
├── plugin.json
├── index.js
├── index.css
└── locales/
    ├── en.json
    ├── zh-CN.json
    └── zh-TW.json
```

> 不要把整个 `dist` 文件夹再套一层放进去。`plugin.json` 如果位于 `...\\snow-file-explorer\\dist\\plugin.json`，宿主将无法按预期加载插件。

### 开发者：从本地构建安装

适合需要试用未发布代码的情况：

```powershell
npm install
npm run build
```

然后在 Snow App 中通过插件管理能力安装本仓库的 `dist` 目录。使用 `config-set` 时，参数如下：

```json
{
  "scope": "plugins",
  "key": "com.github.xqchencn.snow-file-explorer",
  "value": {
    "sourceDir": "D:/path/to/snow-file-explorer/dist"
  }
}
```

将 `sourceDir` 换成你本机 `dist` 的绝对路径。宿主会校验 `dist/plugin.json`，并复制完整插件包到自己的插件目录。

## 快速上手

1. 在 Snow App 中打开一个项目。
2. 打开侧边栏的“文件浏览器”。插件会自动加载当前项目根目录。
3. 左侧入口栏上方在“文件”和“Git 变更”之间切换；下方可打开“运行”和“终端”。
4. 在文件树中点击文件查看内容；点击文件夹展开或收起。
5. 单击 Git 变更文件查看差异，使用右侧查看器在完整文件、统一差异和分栏差异之间阅读变更。

## 功能说明

### 文件树

- 按文件名显示彩色文件图标，并按目录层级浏览项目。
- 右键文件或文件夹可执行：打开、复制路径、复制相对路径、在资源管理器中打开、重命名和删除；这两种条目都还能就地“新建一个文件”——右键文件夹建在它里面，右键文件建在它旁边（跟着人刚点的那一处走，不是每次都回项目根）。建出来的是空文件，建完会在树上展开并打开预览；同名的文件或目录不会被覆盖，项目根以外的位置不建。弹窗那一栏同样写明建在哪个目录。
- 右键文件树空白区域可以在项目根新建一个文件，可以刷新视图，以及切换以下视图选项：
  - **按 `.gitignore` 过滤**：默认开启，隐藏 Git 忽略规则匹配的条目。
  - **Java 包结构视图**：默认开启；识别到 Java 项目时，将连续的包目录折叠成更易读的结构。
- 文件树会显示 Git 状态标记，例如已修改、未跟踪、新增、删除和重命名。

### 文件预览与编辑

- 支持代码文本预览、自动行号和语法高亮。
- 支持 PNG、JPG、SVG、WebP、GIF、ICO、AVIF 等常见图片预览。
- `.md`、`.markdown`、`.mdx` 和 `.mkd` 默认使用 Markdown 预览，可在“预览”和“代码”之间切换。
- Markdown 中的相对路径图片会从当前项目读取并显示。
- 宿主提供写入能力时，可以通过编辑、保存按钮修改文本文件；如果宿主只提供读取能力，界面会显示为只读。
- 代码查看器中的“复制”只复制当前文件内容；文件树右键菜单中的“复制”则用于复制路径或条目操作，请按菜单文字区分。

### Git 变更

切换到“Git 变更”后，可以：

- 查看已暂存和未暂存的文件变更。
- 点击文件查看差异，支持统一视图和分栏视图。
- 单个文件或整个目录暂存、取消暂存。
- 在提交框输入提交信息，点击“提交”或“提交并推送”。
- 使用“AI 生成提交信息”生成提交说明；生成过程中可以停止。
- 丢弃文件更改。

“丢弃更改”不可撤销。提交、推送和同步的具体结果取决于本地 Git 状态、远端地址、认证方式以及网络连接。

顶部同步指示器用于查看本地与远端是否存在待推送或待拉取的提交。它不是 Git 仓库初始化工具；当前目录不是 Git 仓库时，面板会直接显示相应提示。

### REST 请求

左侧入口栏的“REST 请求”会扫描当前项目中的 `.http` 与 `.rest` 文件，按所在目录排布；扫描遵守“按 .gitignore 过滤”开关。列表可键盘操作（Tab 逐行走、Enter 打开、`Enter`/空格展开目录），右键可复制路径、在资源管理器中定位或重新扫描；个别目录读不到时列表会说明结果不完整。要开始一个新文件：列表上方那颗“新建请求文件”建在**当前选中那个请求文件所在的目录**（一个都没选中才建在项目根），右键某个目录则在**那个目录**里建——弹窗那一栏把落点跟着一并报出来（形如“文件名 · api”，就在根下时说“项目根”），给个名字即可（没写扩展名就补 `.http`，这一类文件收 `.http` 与 `.rest` 两种写法，写了别的名字会被当场拦住、“创建”那颗按钮也按不下去），同名文件不会被覆盖，项目根以外的位置不建。点击文件后右侧展开，顶部两个图标切换两种看法：

- **GUI**：每个请求一张卡片，卡片头是标题与发送按钮，默认折叠，点开才摊开方法、地址、请求头、请求体；响应挂在卡片下方。
- **文本**：就是这篇文件本来的代码视图（行号、高亮、复制、右键菜单都在），一进去即可编辑；每条请求那一行的行号上有一个运行箭头，点了就发这一条，位置和 package.json 里脚本的 ▶ 一样。文本态发送时进度与结果走面板状态条，响应本身仍在 GUI 卡片里。

两种看法看的是同一份正文：焦点移开改动处就写回文件，写盘失败会在原地说明原因；“放弃”重读磁盘原文；切到别的视图前也会先把改动落盘。文本态是左右分栏——左边请求代码，右边是最近发出那条的请求体与响应（点左边行号上的 ▶ 就刷新右栏，代码区与光标不动），响应是 JSON 时按缩进逐块折叠、可一键全折/全展；GUI 态则把每条请求摊成一张卡片，响应挂在卡片下方，长正文同样只显示开头并说明。`### 登录` 这类写在分隔行上的文字作为请求标题显示，`# @name` 仍然是请求变量取用的名字。有没写盘的改动时，切换请求文件前会先问一句，不会无声丢弃。

“REST 请求”视图里顶栏不出现运行工具栏，发送每条请求都走它自己那个箭头；同一时刻只发一条，发送期间编辑该请求不会让结果错挂到别的请求上。

文件语法按 [REST Client](https://github.com/Huachao/vscode-restclient) 的实现解析：`###` 分节、请求行可省方法（默认 GET）与尾部 `HTTP/1.1`、`Host:` 头配根相对路径、`?`/`&` 起头的续行、`@name = value` 文件变量（值里可再引用别的变量，转义只还原 `\n` `\r` `\t`，同名后定义覆盖先定义）、`{{ }}` 引用（按 `# @prompt` 填的值 → 系统变量 → 请求变量 → 文件变量 → 环境变量的顺序取值，引用名前加 `%` 表示取值后再做百分号编码）、`# @name` / `@note` / `@no-redirect` / `@no-cookie-jar` / `@prompt` 指令、`X-Request-Type: GraphQL`、正文里的 `< 文件` 与 `<@ 文件` 引用。`#` 与 `//` 开头的注释行不参与语法——注释掉一行头部或正文行就等于删掉它，但注释本身仍留在文件里，GUI 改字段时会按原相对位置带回去。

**环境变量**：环境表存在项目的插件配置目录里——`.snow/.snow-file-explorer/env.json`（公开表，随仓库走）与可选的 `.snow/.snow-file-explorer/env.private.json`（放密钥，同名环境和同名变量都盖过公开表），两份形状都是 `{ "环境名": { "变量名": "值" } }`。位置只认这一处，不逐层向上找：好几份环境表会让人看不出当前用的是哪一份。`$shared` 是保留环境名：里面的变量对所有环境可见，当前环境的同名变量盖过它，界面上会说盖过哪几项；值里可以写 `{{$shared 键}}` 或 `{{本环境名 键}}` 就地取别的环境的值（每次只展开第一处，键名找不到时那句引用原样留着并被点名）。不选环境时只有 `$shared` 生效。GUI 顶部一条环境栏只有三样：环境名的下拉、`$shared` 标记、一颗「修改」。**整张环境表都在那一个弹窗里管，界面上不摊开任何编辑表**：打开时先现读一遍盘（在外面手改过的那一份就在这一步生效），一段一块摊开——已有段的名字只念（改不动），段里是「变量名 / 值」的行，可以加行、删行，段头能把整段删掉（`$shared` 是保留名，不给删），底下「添加环境」再补一段待命名的；「保存」一次写回整张表，「取消」一个字都不写。新段的名字空着、带着路径字符、或跟已有环境重名，都会在窗里当场拦下并说清原因，改完能直接再点一次保存。**环境名和变量名都不能原地改**——名字就是要认的那个名字，要换就删掉那一段、那一行再建一条。写回只碰公开表 `env.json`：私密表里同名的那一项会在它那一行下面点出来（改公开表不生效），只在私密表里的那一段压根不进这张表，也不会被这次保存碰到。这个文件用到了需要有人给值的变量时这一整块才出现——只用系统变量或本篇自己定义了的变量，环境栏一个字都不提。一份环境表都还没有、而又有变量取不到值时，出现的是一句点名缺哪个变量的引导，那颗钮仍然叫「修改」。读坏的那份也会逐条点名（JSON 不合法、形状不对、值不是文字/数字/真假，那一档不生效）。`@name = value` 那一排文件变量**默认收起**，折叠钮钉在环境那一行的最右侧、钮上直接写着「文件变量 9」这样的项数，点开才逐条列出来。同一个弹窗还多一页「文件变量」：本篇的 `@name = value` 逐条只读列在那里，第一页照旧是可改的环境表——这一页答的是「这个值为什么不在环境里」（文件变量同名时盖过环境里的值），要改值仍然只有回文件正文这一处，页里一个输入框都不给；这篇文件没有文件变量时就只有一页，标签条也不摆。点「保存」时整张表若与盘上那一份一字不差，`env.json` 不会被重写一遍。

**`.env`**：`{{$dotenv 键名}}` 取 `.env` 家族的值，只看工作区根那一份：选了环境时先试 `.env.<环境名>`，没有再回落 `.env`。认 `K=V`、`export K=V`、引号包住的多行值与行尾注释，重复键后定义覆盖，`${OTHER}` 不做插值（原样留着）。键名前加 `%` 是两级跳转：先拿当前环境里那个键的值，再用它当 `.env` 里的键名；环境名里带路径字符时不拼 `.env.<环境名>`，免得一份改过的表就把读盘路径带出工作区。

**系统变量**：`$guid`、`$randomInt 起 止`、`$timestamp [±n 单位]`、`$datetime` / `$localDatetime`。后两者除 `rfc1123`、`iso8601` 外还接受引号包住的自定义格式串（`YYYY` `YY` `MMMM` `MMM` `MM` `M` `dddd` `ddd` `DD` `D` `HH` `H` `hh` `h` `mm` `m` `ss` `s` `SSS` `A` `a` `Q` `Z` `ZZ`，`[文字]` 原样输出），后面可再跟偏移（如 `{{$datetime "DD-MM-YYYY" 1 y}}`）。

**请求变量**：`# @name 名字` 之后用 `{{名字.response.body.<JSONPath>}}` 从响应里取值，XML 响应走 XPath（`{{名字.response.body.//reply[1]/@id}}`），`asJson.` / `asXml.` 前缀强制按某一种格式解，`.request.` 取自己刚发出去那份（`body` / `headers`）；同名命中多个只取第一个，没发过的请求会被连名字一起点名。

**curl 块**：一节里第一条非空文本以 `curl` 起头就按 curl 命令还原成请求——`-X/--request`、`-H/--header`、`-b/--cookie`、`-u/--user`、`-d` 一族，行尾 `\` 续行会并起来，多个 `-d` 用 `&` 连接，`-d @文件` 读文件当正文，有正文却没写 Content-Type 时按 `application/x-www-form-urlencoded`，没写方法时有正文按 POST、否则 GET。`-u` 在解析这一步就 base64 了，所以那一格里写 `{{ }}` 不会替换成值。这一节在 GUI 里只读：能直接发送，但改动写不回那行命令，要改就回文本态改它。

**GUI 参数表**：地址带查询串时卡片里地址下面摊一张参数表，加行、删行、改值都只重写 URL 里 `?` 之后那一段，路径与其余部分不动；直接在地址框改也会把参数行跟着重画。

**发出去的正文**按 Content-Type 归置：`application/x-www-form-urlencoded` 的多行用 `&` 连成一行，`multipart/form-data` 用 CRLF 分隔并在结尾补一段 CRLF，`application/x-ndjson` 结尾补换行，GraphQL 的查询与变量拆成 JSON 的两个字段。`Authorization: Basic` 的三种写法（已经是 base64、`user:pass`、`user pass`）都自动补成 `Basic <base64>`。`# @note` 的文案在发送前确认一次。粘贴进来的响应段（以 `HTTP/...` 起头的一节）不进请求清单，界面说明跳过了几段。别的客户端的写法——响应脚本 `> {% … %}` 与响应落盘 `> ./文件`——不属于这份规范：不执行、也不写文件，卡片上各标一条说明，写回文件时原样带回不会丢。

请求由 Snow App 代发，因此有明确边界：只访问 http(s) 完整地址，方法限于 GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS，正文只能是文本（二进制文件正文会被拒绝），重定向始终跟随，请求不带也不保存 cookie，响应体上限 5MB（超过 256KB 的部分界面只显示开头并说明）。遇到做不到的指令时界面会直接说明，而不是假装执行：`@no-redirect` 与 `@no-cookie-jar`、Digest / AWS / COGNITO 三类认证、`$processEnv` 与几个取令牌的系统变量（渲染进程读不到 OS 环境变量与设备令牌）、响应脚本与响应落盘、不支持的正文编码、没填的 `@prompt` 变量、没换成值的 `{{ }}`（连名字一起列出来）、嵌套超过 32 层的变量引用、写错写法的变量定义都会逐条点名。

### 运行与终端

插件将两个工具窗口分开：

- **运行**：从项目配置中识别可运行命令。通过运行工具栏或文件行内的运行按钮启动一次性任务；运行窗口显示输出、退出码，并可停止当前命令。
- **终端**：打开真正可交互的终端，可以在光标处输入命令并连续操作；支持多个终端标签页。

运行命令会使用 Snow App 的终端设置和当前项目目录。项目没有可识别的入口或宿主没有终端能力时，运行入口会提示原因，而不是猜测命令。

运行工具栏常用操作：重新运行、停止当前命令、滚动到底部、清空输出。终端标签页支持新建、关闭，以及右键关闭其他标签页或全部标签页。

### 国际化

插件内置简体中文、繁体中文和英文。显示语言跟随 Snow App 宿主设置。

## 权限与数据边界

插件清单声明了 `filesystem` 和 `terminal` 两类能力：

- `filesystem`：读取当前项目，且仅在用户明确执行打开、保存、重命名、删除等操作时进行相应文件操作。
- `terminal`：仅在用户启动运行命令或终端会话后启动进程，并读取输出和退出状态。

发送 HTTP 请求同样只在用户点击“发送”后进行：请求交由 Snow App 代发，插件不额外收集、保存或上传请求内容，也不保存响应与 cookie。响应正文只保存在当前会话内存中，切换文件或项目即清除。

插件不上传项目文件，也不在插件内保存项目副本。Git 提交、推送以及 AI 提交信息生成是否可用，仍受 Snow App 宿主能力、Git 配置和网络环境影响。

## 常见问题

### 安装后侧边栏没有“文件浏览器”

检查插件目录名称是否为 `com.github.xqchencn.snow-file-explorer`，并确认 `plugin.json`、`index.js`、`index.css` 位于该目录根部。之后完全重启 Snow App。

### 显示“未检测到当前项目目录”

插件跟随宿主的当前激活项目。请先在 Snow App 中打开或切换到一个项目，再刷新文件浏览器面板。

### Git 面板显示“当前目录不是 Git 仓库”

确认当前项目根目录或其上级目录包含 `.git`，并在外部终端执行 `git status` 验证仓库本身可用。插件不会替你初始化仓库。

### 文件可以看但不能保存

这是宿主文件写入能力的限制，不是预览失败。确认 Snow App 当前版本允许插件使用文件写入，并检查插件权限或宿主日志。

### 运行按钮没有可用命令

运行入口来自项目中可识别的配置和入口文件。先确认项目配置存在、文件已保存，并检查宿主是否提供终端能力；需要持续交互时请使用“终端”窗口。

### Release 下载的压缩包无法安装

重新检查压缩包内层级：解压后应直接看到 `plugin.json`。不要把 GitHub 源码压缩包当作插件安装包，也不要把 `dist` 目录作为额外的中间层。

## 从 tag 发布新版本（维护者）

GitHub Actions 会在推送符合 `v*.*.*` 的 tag 时自动发布。发布前只改 `package.json` 的版本号，例如：

```powershell
# package.json version 为 1.0.4 时
 git tag v1.0.4
 git push origin v1.0.4
```

工作流会依次执行依赖安装、ESLint、生产构建和测试，然后：

1. 将 `dist` 内容打成 `snow-file-explorer-v1.0.4.zip`；
2. 生成同名 `.sha256` 校验文件；
3. 创建或更新对应的 GitHub Release，并上传两个文件。

tag 去掉开头的 `v` 后必须与 `package.json.version` 完全一致，否则工作流会在构建前失败。仓库的 Actions 需要允许 `contents: write`，工作流已声明所需权限，不需要额外的发布密钥。

## 本地开发命令

```powershell
npm install          # 安装依赖
npm run check:types  # TypeScript 类型检查（不产出文件）
npm run lint         # 检查源码
npm run build        # 生成 dist 独立安装包
npm test             # 运行测试（需要先生成 dist）
npm run check        # 上面几项一次跑完
```

源码修改应放在 `src/` 和 `locales/`，不要直接编辑 `dist/`。`dist/` 是构建产物，下一次 `npm run build` 会完整重建它。

## 宿主 API 契约（维护者）

插件用 TypeScript 编写，对 Snow App 宿主原始 API（`window.snow`）的调用是强类型的。类型的真源在宿主仓库，不在本仓库：

- `src/types/snow-api.ts` —— 插件实际用到的 33 个 `window.snow` 方法，逐个标注宿主出处
- `src/types/plugin-runtime.ts` —— 宿主注入给插件的运行时 API（`api.t`、`api.storage`、`api.write` 等），手写镜像
- `src/types/prismjs.d.ts` —— `prismjs` 的类型镜像（该包不发类型、本仓也不装 `@types/prismjs`），只覆盖插件用到的 `languages` 与 `highlight`
- `src/types/host/` —— 宿主类型逐字快照，由 `tools/sync-host-api.mjs` 生成，**不要手工编辑**
- `src/components/prism-langs.ts`、`src/icons/icon-data.ts` —— Prism 语言表与 Material 图标数据，由 `tools/generate.mjs` 从依赖里的权威清单生成，**不要手工编辑**（升级 `prismjs` / `material-icon-theme` 后重跑 `npm run generate`）
- `docs/host-api.md` —— 方法清单、宿主文件行号与签名对照表

本机装有 snow-app 源码时，升级宿主后同步一次（路径不同时用 `SNOW_APP_ROOT` 指定）：

```powershell
npm run sync:host    # 从宿主源码重新生成快照
npm run check:host   # 校验快照是否落后于宿主
```

`check:host` 有两层：仓库内文件与 `snapshot.json` 记录哈希的自洽校验（CI 上无宿主仓库也能跑），以及本机存在宿主仓库时追加的漂移校验。

文件改名、删除、写内容走 `api.write.run("filesystem.*")` 而不是原始 API：宿主在这条通道上按 `plugin.json` 的 `privacy.scopes` 做门控。Git 与终端 PTY 宿主没有提供治理动作，只能走 `window.snow`，这是有意为之的分工，细节见 `docs/host-api.md`。
